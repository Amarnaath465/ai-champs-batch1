❌ Traditional Approach

Requirements → [Manual Interpretation] → Code → [Ad-hoc Test]

  • Inconsistent interpretation
  • Missing acceptance criteria
  • Poor traceability
  • Rework cycles (5-7 iterations)
  • No change control

✅ SDD Approach

Spec → Plan → Tasks → Implementation → Validation

  • Clear, testable requirements
  • Defined acceptance criteria
  • Full traceability (req → code → test)
  • Reduced rework (1-2 iterations)
  • Spec-controlled change management

Task Breakdown Example: UART Receive Driver

1
Define Interface Contract — Create uart_receive.h, define signatures, document error codes
Acceptance: Header compiles, API documented
2
Implement Configuration — Create config structure, define baud rate, buffer size
Acceptance: Config structure matches spec
3
Implement Core Logic — Ring buffer, receive state machine
Acceptance: Logic matches state diagram
4
Write Unit Tests — Normal operation, boundary conditions, error handling
Acceptance: All tests pass, coverage > 80%

Change Control Process

1
Submit change request — Document the requested change
2
Impact analysis — Identify affected requirements, code, tests
3
Review and approve — Approve or reject the change
4
Update specification — Revise spec with version control
5
Update implementation — Apply code changes
6
Update tests — Revise test cases
7
Verify traceability — Ensure matrix is updated
8
Close change request — Change complete

Affected Tests: TC-001 (normal receive), TC-003 (timing test)
⚠
Risk: High — timing changes may affect real-time behavior
