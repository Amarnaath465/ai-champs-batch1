What is MCP?
Model Context Protocol — the standard for AI-tool integration
MCP = Model Context Protocol. An open standard that defines how AI models connect to external tools, data sources, and services. Think of it as a USB port for AI — a universal interface that lets any AI agent talk to any tool.
💡
The USB Analogy
Before USB
Every device had a unique connector. Printers, scanners, keyboards — all different. You needed a specific cable for each device.
Before MCP
Every AI tool integration was custom-built. GitHub, Jira, build systems — all different APIs, all different authentication, all different data formats.
After USB
One universal connector. Any device plugs into any computer. Standard power, standard data, standard protocols.
After MCP
One universal protocol. Any AI agent connects to any tool. Standard authentication, standard data format, standard interaction patterns.

Three Core Components
A
AI Agent (Host)
The AI model that wants to use tools. It sends requests to the MCP server and receives results. Examples: Claude, GitHub Copilot, custom agents.
S
MCP Server
The middleware that exposes tools and data to the AI. It translates AI requests into tool calls and returns results in a standard format.
T
Tools & Resources
The actual capabilities: file system access, build commands, test runners, API endpoints, database queries. Each tool has a defined schema.
🔧

PrimitivePurposeExample

How MCP Works (Step by Step)
1. AI receives a task
User asks: "Fix the bug in sensor_poll_all() and write tests." The AI decides it needs tools.
2. AI requests available tools
AI queries the MCP server: "What tools can I use?" Server returns: read_file, run_tests, create_pr, etc.
3. AI calls a tool
AI calls read_file("sensor_poll.c"). MCP server executes the tool and returns the file contents.
4. AI processes result
AI reads the code, understands the bug, generates a fix, and calls write_file() to apply it.
5. AI verifies
AI calls run_tests(). Tests pass. AI calls create_pr() with the fix and test evidence.
Reusable Skills
Package MCP workflows into repeatable, shareable capabilities
Skills = codified workflows. A skill is a reusable MCP workflow that captures a specific engineering task: how to pull an issue, how to write a spec, how to run tests, how to create a PR. Skills are shared across the team and improve over time.
📚
What is a Skill?
Skill = Recipe
Like a recipe: step-by-step instructions for a specific dish. Anyone can follow it and get the same result. Skills capture engineering workflows the same way.
Skill = Test Pattern
Like a test pattern: a proven approach to a common problem. You don't reinvent the solution each time — you apply the pattern. Skills are the same for engineering workflows.
🔧
Skill Anatomy
# Skill: fix-issue # Trigger: "fix the bug in #142" # Steps: 1. READ issue from GitHub/Jira → Extract: description, acceptance criteria, priority 2. LOCATE relevant code → Search codebase for related functions, files, tests 3. ANALYZE root cause → Read code, trace call hierarchy, identify bug 4. IMPLEMENT fix → Apply minimal change, follow coding standards 5. TEST the fix → Run existing tests, add new test for the bug 6. CREATE PR → Title, description, traceability, test evidence 7. REQUEST human review → Flag for human approval before merge
✓
Benefits of Reusable Skills
1
Consistency
Every team member gets the same workflow. No individual variations, no missed steps. Quality is predictable.
2
Improvement
Skills improve over time. When someone finds a better approach, the skill is updated. Everyone benefits from the improvement.
3
Shareability
Skills are shared across teams and projects. A good fix-issue skill works for embedded firmware and web apps.
🛠
Embedded-Specific Skills
analyze-blast-radius ▼
Given a function or module to change: map all callers, dependents, tests, and configuration touchpoints. Output a blast-radius report with risk assessment. Used before any brownfield change.
write-spec-for-issue ▼
Read a GitHub/Jira issue, analyze the codebase context, and generate a complete specification with requirements, constraints, interfaces, and acceptance criteria. Follows the SDD five-point quality bar.
generate-tests-from-spec ▼
Read a specification and generate unit tests for each acceptance criterion. Includes boundary tests, error-path tests, and mock setup. Uses the project's test framework.
validate-regression ▼
Run the full test suite before and after a change. Compare results, identify regressions, and produce a regression report. If regressions found, suggest rollback strategy.

🔄
Workflow Step by Step
1. Pull Issue
AI reads the issue from Jira/GitHub via MCP. Extracts: description, acceptance criteria, priority, related context. No manual copy-paste.
2. Locate Code & Docs
AI uses MCP to search the repository: find related files, read documentation, trace dependencies. Repository-aware navigation.
3. Implement Fix
AI implements the change using Copilot. Minimal diff, follows coding standards, respects existing patterns. Uses context from the spec.
4. Run Build
AI calls make or equivalent via MCP. Verifies compilation succeeds. If build fails, diagnoses and fixes before proceeding.
5. Run Tests
AI calls make test via MCP. Verifies all tests pass. If tests fail, diagnoses the failure and fixes it. Runs regression suite.
6. Create PR with Evidence
AI creates a PR with: description linking to the issue, test results, build log, traceability matrix. Evidence included automatically.
7. Human Review Gate
AI requests human review. Human reviews the PR with full context. Approves, requests changes, or rejects. Human is always in the loop.
⚠
Human Oversight is Non-Negotiable
AI automates the routine work — locating code, implementing fixes, running tests, creating PRs. But the human review gate is never automated. You approve. You decide. AI assists; humans decide.
AI handles: Code navigation, implementation, test generation, build execution, PR creation, evidence collection.
Human decides: Code review, architectural decisions, merge approval, exception handling, production deployment.
