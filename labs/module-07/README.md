# Module 07 — Guided Lab: MCP-Enabled Agentic Embedded Engineering

**Duration:** 2 hours | **Format:** Guided Build Lab | **Audience:** All roles, technical hands-on depth for Embedded/Firmware Developers, Architects, Testers, DevOps/SRE, Engineering Leads

Connects an AI agent to a real engineering system — Atlassian Jira — through MCP, then runs one real issue through the full loop the cohort described unprompted in the calibration survey: **issue → spec → implementation → evidence → status update.** This module ships one small, real fix to `sample-repo`, driven end to end by a Jira story instead of a copy-pasted prompt.

---

## Learning Objectives

By the end of this lab, you will have:

1. Connected an MCP-capable AI agent (GitHub Copilot) to Atlassian Jira, and confirmed exactly which tools that connection grants — no more, no less.
2. Created a real, simple Jira user story for a genuine, already-documented gap in `sample-repo`.
3. Turned that story into a spec using the real GitHub Spec Kit CLI (`/speckit-specify` → `/speckit-plan` → `/speckit-tasks`), continuing the numbered `specs/NNN-.../` convention from Module 04's bonus exercise.
4. Implemented the fix, proved it with a real test and a sanitizer run, and assembled the same kind of evidence package Module 06 required.
5. Closed the loop by transitioning the Jira issue's status and attaching evidence — the one step no earlier module touched.
6. Practiced the permission discipline from Slide 7: read Jira freely, write to Jira only with an explicit, visible tool call you approved.

## The Real Gap Driving This Lab

This lab is not a synthetic prompt. `docs/CODE_REVIEW_REPORT.md` (produced against `sample-repo` earlier in the programme) already contains a genuine, unresolved **High** finding:

> **File:** `src/diag_formatter.c:13` — `snprintf(..., "%s", detail)` is called without checking whether `detail` is `NULL`. Passing `NULL` can cause undefined behavior or a crash on some libc implementations.

Verified before writing these instructions: on this host's libc, calling `diag_format_message(buf, len, code, NULL)` today happens to print the literal text `(null)` rather than crashing — but that's an implementation courtesy, not a guarantee, and it's exactly the kind of behavior that *does* crash on a leaner embedded C library. `tests/test_diag_formatter.c` confirms the gap independently: every existing test passes a real string for `detail`; none passes `NULL`. Nothing in the shipped suite exercises this path today.

That's today's whole feature: **make `diag_format_message` handle a missing `detail` safely, and prove it with a test.** Small on purpose — the point of this module is the MCP/Jira/Spec Kit/evidence loop, not the size of the fix.
