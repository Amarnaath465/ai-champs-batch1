Verity (Verify)

Check output against requirements
Embedded Verification:
  • Does compiled code match spec?
  • Memory usage within budget?
  • Timing constraints met?
  • Test coverage acceptable?

Iteration (Refine)

Iterate on output quality
Refinement Strategy:
  • Review generated code against patterns
  • Add missing error handling
  • Refine naming to match conventions
  • Ensure MISRA-C compliance

Decomposition (Break Down)

Split complex tasks into subtasks
Decomposition Example:
  • 1. Generate HAL interface header
  • 2. Implement driver functions
  • 3. Add error handling
  • 4. Write unit tests

Examples (Show/Teach)

Provide code examples for the model
Embedded Examples:
  • Similar driver implementations
  • Existing HAL usage patterns
  • Test file templates
  • Error handling conventions

Constraints (Boundaries)

Define limits and rules
Embedded Constraints:
  • No dynamic allocation
  • Must use HAL library
  • Max 1KB RAM usage
  • MISRA-C compliant

Instructions (What to Do)

Clear task specification
Effective Instructions:
  • "You are an embedded software engineer specializing in C/C++ firmware"
  • "Implement a circular buffer for UART receive"
  • "Follow these constraints..."

Task Framing (Clear Objective)

Define what success looks like
Task Framing Components:
  • Objective: What to implement
  • Scope: Boundaries (e.g., "Only TX/RX, no flow control")
  • Constraints: Limits (e.g., "Must use HAL library, < 1KB RAM")
  • Output: Expected result (e.g., "C source + header + unit tests")

Context Engineering vs Prompt Engineering

Context engineering is the multiplier — it determines WHAT information you provide, not just how you ask.

✍ Prompt Engineering

  • Focuses on HOW you ask
  • Instruction wording and structure
  • Task decomposition
  • Example selection
  • Iterative refinement

📁 Context Engineering

  • Focuses on WHAT information you provide
  • Repository content selection
  • Design document inclusion
  • Interface contract exposure
  • Token budget management
✨ Combined Effect:

Clear instructions + Right context = Best output. Poor context limits even the best prompts. Context engineering is the multiplier.

Context Layering Strategy

Click each layer to see details and when to include it.

Layer 5: History

Issue context, past changes

When to include: When debugging regressions or understanding why a change was made.
Content: Bug reports, recent commits, change rationale.
Token cost: Low — reference issue numbers, not full history.

Layer 4: Standards

Coding rules, style guides

When to include: Always — for compliance and consistency.
Content: MISRA-C rules, naming conventions, formatting standards.
Token cost: Medium — include relevant rules only, not full standard.

Layer 3: Design

Architecture, diagrams

When to include: When changing structure or adding new modules.
Content: Architecture docs, module responsibilities, design decisions.
Token cost: Medium — extract key decisions, not full documents.

Layer 2: Interface

HAL boundaries, contracts

When to include: When modifying interfaces or cross-module interactions.
Content: Header files, API contracts, HAL function signatures.
Token cost: High — include full interface definitions.

Layer 1: Core

Task file + dependencies

When to include: Always — this is the foundation.
Content: Direct task files, immediate dependencies, related source/headers.
Token cost: Highest — allocate 60% of budget here.

Avoiding Context Inflation

❌ Anti-Patterns

  • Paste entire repository
  • Include all header files
  • Add unrelated test files
  • Include full build logs
  • Paste complete configuration files

✅ Best Practices

  • Select specific files relevant to task
  • Include only affected interfaces
  • Reference design docs by path, not content
  • Summarize build configuration
  • Include only relevant code snippets

Task-Scoped Context Patterns

Three patterns for structuring context based on the type of engineering task.

🚀 New Feature Implementation Pattern

Use when implementing new functionality. Context flows from specification outward.

1
Feature Specification — Requirements, acceptance criteria, constraints
2
Affected Interfaces — Header files, HAL boundaries, data structures
3
Existing Patterns — Similar implementations, coding conventions, test patterns

🐛 Bug Fix / Regression Pattern

Use when fixing bugs or investigating regressions. Context focuses on the problem and its history.

1
Error Description — Symptom + reproduction steps
2
Affected Code — Function with bug + related tests
3
History — Recent changes, commit log, regression source
4
Constraints — Timing, memory, backward compatibility

🔧 Refactoring Pattern

Use when restructuring code. Context defines current state, target state, and safety boundaries.

1
Current State — Function/file to refactor, current behavior, known issues
2
Target State — Desired behavior, quality goals, constraints
3
Safety Boundaries — Interface contracts to preserve, tests to maintain

Prompt-Only vs Context-Engineered

❌ Prompt-Only

"Write a UART driver"

  • No repository structure
  • No HAL boundaries
  • No coding standards
  • No existing patterns

Result: Generic, may not match project conventions

✅ Context-Engineered

"Write a UART driver"

  • uart.h (interface)
  • hal.h (HAL API)
  • coding_standards.md
  • similar_driver.c (example)

Result: Targeted, follows project conventions
