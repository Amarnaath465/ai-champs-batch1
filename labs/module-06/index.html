Test Strategy
What to test, when to test, and how to prove it
Test strategy is not optional. Without a strategy, testing is ad-hoc — some things get tested, others don't, and you never know which. A test strategy defines what gets tested, at what level, with what tools, and how results are measured.
Three Pillars of Test Strategy
1
What to Test
Map tests to spec acceptance criteria. Every criterion must have at least one test. If it's not testable, it's not a valid criterion.
2
How to Test
Choose the right test level (unit/integration/E2E) for each criterion. Unit tests for logic, integration for interfaces, E2E for critical paths.
3
When to Test
Test at the right time: unit tests during implementation, integration tests after module integration, regression tests on every commit.
📋
Spec-to-Test Mapping
The bridge between specification and testing: every acceptance criterion maps to a test. This is how you prove the implementation matches the spec.

Embedded-Specific Test Categories
Functional Tests — Does it do what the spec says? ▼
Core correctness tests. For each function: verify outputs for valid inputs, verify error handling for invalid inputs, verify edge cases (empty, null, max-size). These are the most common and most valuable tests.
Boundary Tests — What happens at the edges? ▼
Test at the boundaries of valid ranges: minimum values, maximum values, off-by-one, empty inputs, full buffers. In embedded: test with zero sensors, one sensor, maximum sensors. Test with empty buffers, full buffers, overflow conditions.
Error Path Tests — What happens when things go wrong? ▼
Test error handling: what happens when a function receives invalid parameters, when a resource is unavailable, when a timeout occurs. Error paths are often untested because they're harder to trigger — but they're where bugs hide.
Performance Tests — Does it meet timing constraints? ▼
In embedded, correctness isn't enough — the code must also meet timing constraints. Measure worst-case execution time, average latency, throughput. Compare against the spec's timing requirements. Use profiling tools or instrumented builds.
Resource Tests — Does it fit in the budget? ▼
Embedded systems have fixed memory budgets. Test stack usage, heap allocation, static memory usage. Verify the code fits within the target's memory map. Resource overruns cause hard-to-debug crashes in the field.
Mocks & Stubs
Isolate components for testing — remove hardware dependencies
The embedded testing challenge: You can't test hardware-dependent code on your laptop. Mocks and stubs replace hardware dependencies with可控 substitutes, enabling unit testing without the target device.
S
Stubs
Return fixed values. simplest form of test double. Replace a dependency with a function that returns a predetermined value.
// Stub: always returns 42 int adc_read(uint8_t ch) { return 42; }
F
Fakes
Working implementations simplified for testing. More realistic than stubs — maintain state but without hardware/OS dependencies.
// Fake: in-memory FIFO typedef struct { uint8_t buf[256]; size_t head, tail; } fake_fifo_t;
M
Mocks
Verify interactions. Record calls, check parameters, enforce call order. Most powerful but most complex test double.
// Mock: verify call + args EXPECT_CALL(mock, send(0x05)) .Times(1); EXPECT_CALL(mock, receive()) .WillOnce(Return(0x0A));
🔍
When to Use Each
Test DoubleUse WhenComplexityBest For
Stub You need a fixed return value Low Simple input/output tests
Fake You need realistic behavior without hardware Medium Data structures, protocols, state machines
Mock You need to verify how code interacts with dependencies High API contracts, call sequences, error propagation
🔧
Common Embedded Mocks
HAL Mocks ▼
Replace hardware abstraction layer calls: GPIO read/write, UART send/receive, timer operations. Enable testing application logic without hardware. Example: mock gpio_read() to return controlled values.
Communication Mocks ▼
Replace SPI, I2C, UART, CAN interactions. Return controlled responses, inject errors, simulate timeouts. Enable testing protocol handlers without real buses.
Timer Mocks ▼
Replace hardware timers with controllable time sources. Advance time artificially, trigger callbacks at specific moments, test timeout handling without real delays.
RTOS Mocks ▼
Replace RTOS primitives: mutex, semaphore, queue operations. Test thread-safe code without a real RTOS. Verify correct use of synchronization primitives.
Regression Testing
Ensure changes don't break what already works
Regression = safety net. Every time you change code, you risk breaking something that was working. Regression testing is the process of verifying that existing behavior is preserved after changes.
Regression Strategy
Three layers of regression protection
1
Smoke Tests
Quick sanity checks. Does the system boot? Do core functions work? Run on every commit. Takes seconds, catches showstoppers.
~30 seconds Every commit
2
Regression Suite
Full test suite from all previous passes. Every test that ever caught a bug stays in the suite forever. Runs on every PR.
~5-15 minutes Every PR
3
Full Validation
Complete regression + performance + resource tests. Runs before major releases or when timing/memory-sensitive changes are made.
~30-60 minutes Pre-release
🔄
Regression Test Workflow
Baseline: All tests green
Before any change, verify the full test suite passes. If tests are already failing, fix them first.
Make your change
Implement the change per your plan. One logical change at a time.
Run regression suite
All existing tests must still pass. If any fail, revert and diagnose before proceeding.
Add new tests
Write tests for the new behavior. Run full suite including new tests.
Commit with confidence
Full suite green, new tests green. Document what was verified.
⚠
Regression Anti-Patterns
The Flaky Test ▼
Tests that sometimes pass, sometimes fail — for no clear reason. Fix immediately. Flaky tests destroy confidence in the test suite. Common causes: timing dependencies, shared state, hardware races.
The Silent Deletion ▼
Deleting a test because it fails instead of fixing the code. Never delete a failing test without understanding why it fails. A failing test is telling you something important.
The Stale Test ▼
Tests that pass but no longer test the right thing. When requirements change, tests must change too. Review tests when you update specs — stale tests give false confidence.
The Integration-Only ▼
Only running integration/E2E tests, skipping unit tests. Integration tests are slow and hard to debug. Unit tests are fast and pinpoint issues. You need both.
AI-Assisted Testing
Use Copilot to generate, improve, and analyze tests
AI's sweet spot: Test generation is one of the highest-value uses of AI in embedded development. Tests are repetitive, pattern-based, and follow predictable structures — exactly what AI excels at. But always verify the generated tests.
🤖
AI-Assisted Testing Workflow
1. Provide context
Give Copilot the spec, function signature, and edge cases. More context = better tests.
2. Generate test skeleton
Ask Copilot to generate test cases from the spec's acceptance criteria. Review the structure.
3. Review and correct
Verify tests are correct: do they test the right thing? Are edge cases covered? Is the assertion correct?
4. Run and verify
Run the tests. All should pass. If a test fails, diagnose: is the test wrong or the code?

Embedded Testing Challenges
Unique constraints that make embedded testing harder
Why embedded testing is different: You can't just npm test and walk away. Embedded systems have hardware dependencies, real-time constraints, fixed memory budgets, and safety requirements that don't exist in application software.
🔌
Hardware Dependencies
Code that interacts with hardware can't run on a development machine. Solution: mock the HAL layer, test logic separately from hardware.
Strategy: Abstract hardware behind HAL interfaces. Mock HAL for unit tests. Test on real hardware only for integration/E2E.
⏱
Real-Time Constraints
Tests must complete within timing budgets. A test that takes 10 seconds to run can't be in the commit-stage pipeline. Solution: tiered test execution.
Strategy: Fast unit tests for commit stage. Slower integration for PR stage. Full validation for release stage.
💾
Fixed Memory Budget
Can't just allocate more memory if tests need it. Test code must fit alongside application code. Solution: test on host with generous memory, on-target with budget checks.
Strategy: Host tests for logic, on-target for resource verification. Track test code size impact.
⚠
Interrupt Safety
Code running in interrupt context has different constraints. Tests must verify: no blocking, no allocation, no non-atomic shared access. Solution: dedicated interrupt-context tests.
Strategy: Static analysis for ISR rules. Unit tests with simulated interrupt preemption. Integration tests with real interrupts.
