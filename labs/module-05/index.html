Step 1: Specify — Write the Specification
The foundation of greenfield SDD. A well-written specification defines what the feature must do before anyone writes a line of code.
Five-point spec quality bar: precise signature, behaviour under edge cases, error-code ranges, empty/buffer-too-small cases, priority rules for simultaneous conditions.
spec.md
Requirements, constraints, interfaces & contracts, acceptance criteria
Acceptance Criteria
Traceable, testable conditions that define "done"
🛠
Step 2: Architect — Design the Architecture
Define module boundaries, data flow, API contracts, and integration points. In embedded: decide on HAL boundaries, memory allocation strategy, and real-time constraints.
Architecture decisions are spec-driven: The specification's constraints (memory limits, timing, interface contracts) directly shape architectural choices. Don't design architecture in isolation.
Module Boundaries
What each module owns, interface contracts between them

Step 3: Plan — Generate Implementation Plan
Break the specification into an ordered, traceable task list. Each task maps to one or more acceptance criteria. Use AI (Copilot) to generate the plan, then review for correctness.
Task traceability: Every task in tasks.md must reference a requirement or acceptance criterion from spec.md. No orphan tasks, no undocumented work.

Step 4: Implement — Code Against the Spec
Task-by-task implementation with Copilot. Each diff is checked against its acceptance criterion as it lands. No "build first, spec later" — the spec drives every line.
Key discipline: After each task, verify the implementation matches the spec's acceptance criteria. If the code does something the spec doesn't cover, either update the spec or remove the code.

Step 5: Test — Verify Against the Spec
Write tests that prove each acceptance criterion is met. Tests are not an afterthought — they're generated from the spec. If a criterion has no test, the criterion isn't done.
Test = Proof: Every acceptance criterion maps to at least one test. A passing test suite is proof that the implementation matches the specification.

Build a traceability matrix: every acceptance criterion → implemented code → test → passing. Audit against SDD anti-patterns. This is the "receipt" that proves the feature was built correctly.
Traceability matrix: A living document that proves every acceptance criterion maps to implemented, tested, passing behavior. If any criterion has no mapping, the feature isn't done.

Step 1: Repo Archaeology — Understand What Exists
Before touching any code, you must understand the existing architecture. Repository archaeology is the systematic process of discovering how the codebase is structured, what each module does, and where the boundaries are.
Key insight: 42% of the cohort report fragmented change-impact analysis as their top pain point. Repository archaeology addresses this directly — structured discovery beats ad-hoc code reading.

Step 2: Analyze — Impact Assessment
Identify exactly what your change will touch. Map the blast radius: which functions, which modules, which tests. Understand the dependencies before writing a line of new code.
Blast radius: For every change, ask: "What else calls this function? What depends on this module? What tests will break?" Answer these before coding.

Step 3: Specify — Write a Change Specification
Even for brownfield changes, write a spec. It's shorter than a greenfield spec but equally important: what's changing, what's staying the same, what must not break, and how you'll verify it.
Brownfield spec extras: Add a "must not break" section — list the existing behaviors that must remain unchanged. Add a "regression risk" section — identify the highest-risk areas.
Change Spec
What's changing, what's not, what must not break
Regression Risk

📋
Step 4: Change Plan — Minimal Diff Strategy
Plan the smallest possible change that satisfies the spec. In brownfield, "less is more" — every extra line of code is a potential regression risk. Plan for minimal surface area.
Minimal diff principle: The best brownfield change is the smallest one that works. If you can add 10 lines instead of 50, do it. If you can modify one function instead of three, do it.
Change Plan

Step 5: Implement — Safe, Incremental Changes
Implement one change at a time. After each change, run existing tests to verify nothing broke. Only proceed when the test suite is green. Never make two changes at once.
One change, one test run: The cardinal rule of brownfield development. Make a change. Run the tests. If green, proceed. If red, revert and diagnose. Never stack changes.

Step 6: Validate — Prove Nothing Broke
Final validation: run the full test suite, verify the change spec's acceptance criteria, and confirm backward compatibility. Document what changed and what was verified.
Validation checklist: (1) All existing tests pass. (2) New tests pass. (3) Change spec criteria met. (4) No undocumented side effects. (5) Code review approved.

Repository Archaeology
Systematic discovery — understand the codebase before changing it
The #1 pain point from the cohort: 42% report fragmented change-impact analysis — reading code, tracing call hierarchies, dependency analysis, build/config analysis, all done ad-hoc with no set approach. Repository archaeology replaces ad-hoc with systematic.
Core Techniques
Click each technique to learn more
🔍 Dependency Mapping ▼
Map what depends on what. In C/C++ firmware, this means: which .c files include which .h files, which functions call which other functions, which modules depend on which HAL interfaces. Start from the change point and trace outward. AI tools can accelerate this — ask Copilot to list all callers of a function, or trace include chains.
🔗 Call Hierarchy Tracing ▼
For the function you're modifying, trace the complete call chain: who calls this function, and who calls them? This reveals the full blast radius. In embedded systems, call hierarchies often cross module boundaries — a state machine callback might trigger a HAL call, which triggers an interrupt handler. Map the full chain.
🛠 Build System Analysis ▼
Understand the build system before making changes. Which Makefile/CMake rules compile which files? Are there conditional compilation flags? What libraries are linked? Build system changes can have unexpected side effects — know the structure before touching it.
📄 Configuration Archaeology ▼
Embedded systems often have configuration files, header files with #define constants, or linker scripts that control behavior. Understanding these is critical — a change to a config value can affect memory layout, timing, or behavior across the entire system. Map all configuration touchpoints before changing anything.
📈 Test Inventory ▼
What tests exist? What do they cover? Which tests are relevant to the area you're changing? In brownfield work, knowing your test coverage is as important as knowing your code coverage. If there are gaps, you need to fill them before making changes.

Safe Change Strategy
Minimal diff, maximum safety — the brownfield engineering discipline
Core Principles
Non-negotiable rules for brownfield changes
✓
Minimal Surface Area
Change the fewest files, functions, and lines possible. Every extra line is a potential regression. If you can solve the problem in 10 lines, don't write 50.
✓
One Change at a Time
Never stack changes. Make one change, run tests, verify green, then make the next. If something breaks, you know exactly which change caused it.
✓
Backward Compatibility
Existing APIs, interfaces, and behaviors must remain unchanged unless the spec explicitly says otherwise. New behavior is additive; existing behavior is sacred.
✓
Test-Driven Safety
Run the full test suite after every change. If a test fails, diagnose before proceeding. Never assume a failure is "expected" — verify it.
🔧
Embedded-Specific Safety Considerations
Embedded brownfield changes have unique risks that don't exist in application software.
Memory Layout ▼
Changes to struct sizes, array dimensions, or allocation patterns can shift memory layout. In embedded, this can affect timing, stack usage, and even hardware register mapping. Always verify memory usage after changes.
Timing Constraints ▼
A function that was previously safe might become a timing hazard if its execution time increases. In real-time systems, worst-case execution time matters more than average. Profile before and after changes.
Interrupt Safety ▼
If your change touches code that runs in interrupt context, you must verify: no blocking calls, no dynamic allocation, no non-atomic operations on shared data. Interrupt safety bugs are among the hardest to reproduce and debug.
HAL Boundaries ▼
Hardware Abstraction Layer interfaces are contracts. Changing a HAL function's signature or behavior affects every caller. If you must change a HAL interface, update every caller and every mock.

Regression Protection
Prove nothing broke — the safety net for brownfield changes
The brownfield fear: "I changed one function and three modules broke." Regression protection is the systematic process of ensuring your change doesn't break existing behavior — and proving it with tests.
Regression Strategy
Three layers of regression protection
1
Existing Tests
Run the full existing test suite before and after your change. If all tests pass before and after, existing behavior is preserved. This is your baseline safety net.
2
New Tests
Write tests for the new behavior. These prove your change does what the spec says. Without new tests, you're trusting the implementation without proof.
3
Boundary Tests
Test the boundaries: edge cases, error paths, empty inputs, maximum sizes. These catch the regressions that normal tests miss — the ones at the edges of the spec.
🔄
Regression Test Workflow
Baseline: Run full test suite
Before any change, verify all existing tests pass. If tests are already failing, fix them first — don't stack new changes on broken tests.
Make one change
Implement the smallest possible change per your change plan.
Verify: Run full test suite again
All existing tests must still pass. If any fail, revert immediately and diagnose.
Add new tests
Write tests for the new behavior. Run full suite including new tests.
Final verification
Full suite green. New tests green. Change complete. Document what was verified.

⚠
When Tests Fail: The Decision Tree
A failing test after a brownfield change is expected behavior — it means your safety net is working. Follow this decision tree:
1. Is this a pre-existing failure? → Run the test suite on the original code (before your change). If it fails there too, the issue is pre-existing — fix it separately.
2. Did your change break it? → Revert your change. If the test passes again, your change caused the regression. Diagnose the root cause before re-implementing.
3. Is the test wrong? → If the test was testing the wrong behavior, update the test — but only after confirming with the spec and team. Never silently delete a failing test.
4. Is this expected new behavior? → If your change intentionally alters behavior (per the spec), update the test to match the new spec. Document the change in the traceability matrix.
