Risk Patterns & Litmus Test

Unmanaged AI usage creates real engineering risks in safety-critical embedded systems.

Common Risk Patterns

💥 Silent Architecture/Standards Violations

AI generates code that compiles and runs but breaks architectural patterns or coding standards without obvious warning signs.

🔄 Hard-to-Diagnose Brownfield Regressions

AI modifications to existing firmware introduce subtle behavioral changes that escape basic testing.

🤔 Closed-Toolchain/RTOS Hallucination

AI suggests code using APIs, libraries, or RTOS features that don't exist in the target toolchain.

📝 Spec-Free Prompt-Only Development

Skipping specification leads to inconsistent interpretation, missing acceptance criteria, and rework cycles.

📈 Context Inflation/Token Waste

Dumping entire repositories into prompts wastes tokens and dilutes context, producing lower quality output.

💰 Zero Cost/Usage Visibility

No tracking of AI consumption means cost leakage, unmeasured quality, and no ROI data for governance.

🧭 The Litmus Test

“Would we approve a PR that compiles, passes tests, and meets spec — but uses more memory than budgeted, breaks a design pattern, or regresses timing under load?”

Near-unanimous NO from the cohort. Passing tests and meeting spec are necessary but not sufficient. Non-functional criteria (memory, timing, patterns) must be first-class gates, not soft advisories.
